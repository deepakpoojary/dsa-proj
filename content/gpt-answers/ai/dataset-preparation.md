Preparing a fine-tuning dataset means turning your real use case into **clean, consistent, well-formatted input/output examples** that show the model exactly the behaviour you want. In fine-tuning, the quality of the data matters far more than its size.

## 1. Define the target behaviour

Before collecting anything, write down what "good" looks like:

- What tasks should the model do (classify tickets, answer in a brand voice, output JSON)?
- What format, tone and length should answers have?
- What should it **refuse** or say "I don't know" to?

If you cannot describe a good answer clearly, the dataset will be inconsistent and the model will learn that inconsistency.

## 2. Collect raw examples

Good sources:

- **Production logs** (real user inputs) with answers corrected by experts
- **Support tickets, emails, internal docs** paired with ideal responses
- **Synthetic data** generated by a stronger model, then filtered and reviewed

For LoRA / supervised fine-tuning (SFT), a few hundred to a few thousand **high-quality** examples is often enough.

## 3. Format as chat records

Most modern fine-tuning uses JSONL with chat messages, matching the template used at inference time:

```python
import json

example = {
    "messages": [
        {"role": "system", "content": "You are a support assistant for Acme."},
        {"role": "user", "content": "How do I reset my password?"},
        {"role": "assistant", "content": "Go to Settings > Security > Reset password, then follow the email link."},
    ]
}

with open("train.jsonl", "a", encoding="utf-8") as f:
    f.write(json.dumps(example, ensure_ascii=False) + "\n")
```

Use the **same system prompt and chat template** you will use in production; otherwise the model sees a different distribution at inference.

## 4. Clean the data

- **Deduplicate** exact and near-duplicate examples (e.g. with MinHash or embedding similarity)
- **Remove PII and secrets** (emails, phone numbers, API keys)
- **Fix label noise**: wrong answers, inconsistent styles, outdated facts
- **Drop** truncated, empty or off-policy responses
- **Check token lengths** so examples fit the context window

## 5. Balance and cover the distribution

- Balance classes and topics so one category does not dominate
- Include **edge cases**, ambiguous inputs and multi-turn conversations
- Add examples of **refusals** and "insufficient information" answers
- Keep style consistent across annotators (write a short labelling guide)

## 6. Split correctly

| Split | Purpose | Typical size |
|---|---|---|
| Train | Model learns from it | 80-90% |
| Validation | Tune hyperparameters, early stopping | 5-10% |
| Test (held-out) | Final, untouched evaluation | 5-10% |

Avoid **leakage**: split by user, document or conversation rather than by row, and dedupe across splits.

## 7. Training details that depend on the data

- **Loss masking**: compute loss only on assistant tokens, not on the prompt
- **Epochs**: small datasets overfit quickly; watch validation loss
- **Licensing**: confirm you have the rights to use every source

## Common pitfalls

- Optimising quantity over quality (thousands of noisy examples hurt more than they help)
- Training on data that contains the eval set
- Teaching facts via fine-tuning when **RAG** would be better (fine-tuning is best for format, style and behaviour)
- Unreviewed synthetic data that amplifies a teacher model's mistakes

## Summary

- Start from a clear definition of good output and real inputs.
- Format as chat JSONL with the production template, then clean, dedupe, redact and balance.
- Split without leakage and keep a held-out test set to prove the fine-tune actually helped.
