You evaluate a RAG system by measuring the **retrieval** step and the **generation** step separately, then the **end-to-end** answer quality, using a representative test set plus automated metrics, LLM-as-judge grading and human review. Splitting it up this way tells you *where* a failure comes from, not just *that* something failed.

## 1. Build an evaluation dataset

Everything starts with a **golden dataset**:

- **Real user questions** (from logs, support tickets or domain experts)
- **Expected answers** and/or the **source documents or chunks** that contain them
- A mix of difficulty: simple lookups, multi-hop questions, ambiguous questions, and **unanswerable** questions (the system should say "I don't know")

Start with 50-200 high-quality examples. Synthetic questions generated by an LLM from your docs can add coverage, but review them, because they tend to be too easy.

## 2. Evaluate retrieval

*Did we fetch the right context?*

| Metric | What it tells you |
|---|---|
| **Recall@k** | Share of relevant chunks that appear in the top k |
| **Precision@k** | Share of the top k that are relevant |
| **Hit rate@k** | Whether at least one relevant chunk appears in the top k |
| **MRR** | How high the first relevant result ranks |
| **nDCG@k** | Ranking quality with graded relevance |

```python
def recall_at_k(retrieved_ids, relevant_ids, k=5):
    top = set(retrieved_ids[:k])
    return len(top & set(relevant_ids)) / len(relevant_ids)

def mrr(retrieved_ids, relevant_ids):
    for rank, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in relevant_ids:
            return 1 / rank
    return 0.0
```

Use these numbers to compare chunk sizes, embedding models, hybrid search and rerankers.

## 3. Evaluate generation

*Given the context, is the answer good?*

- **Faithfulness / groundedness**: is every claim supported by the retrieved context? This is your hallucination metric.
- **Answer relevance**: does the answer address the question?
- **Correctness**: does it match the reference answer?
- **Citation accuracy**: do the cited sources actually support the claims?
- **Context utilisation**: did it use the relevant context it was given?

These are usually scored with **LLM-as-judge**:

```python
JUDGE_PROMPT = """You are grading a RAG answer.
Context:
{context}

Answer:
{answer}

List each factual claim in the answer and mark it SUPPORTED or UNSUPPORTED
by the context. Then output a JSON object: {{"faithfulness": <supported / total>}}"""
```

**Calibrate the judge**: have humans label a sample and check that the judge agrees with them. Use clear rubrics, binary or low-scale scores, and a strong judge model.

## 4. End-to-end and operational metrics

- **Task success rate** on the golden set
- **Refusal behaviour**: does it correctly decline unanswerable questions, and avoid declining answerable ones?
- **Latency** (p50/p95), **cost per query**, and **tokens per answer**
- **Safety**: prompt-injection resistance and PII leakage

## 5. Tooling

- **Ragas**: faithfulness, answer relevancy, context precision and recall
- **DeepEval, TruLens, promptfoo**: test-style evals that can run in CI
- **LangSmith, Langfuse, Arize Phoenix**: tracing plus datasets and experiments

## 6. Make it continuous

```
change (prompt / chunking / model) ─► run eval suite in CI ─► compare to baseline ─► ship or reject
production traffic ─► traces + user feedback ─► sample failures ─► add to golden set
```

- Track metrics over time so you notice **regressions**.
- Use **thumbs up/down** and escalation data as online signals.
- A/B test big changes on live traffic when possible.

## Common mistakes

- Judging only the final answer, so you cannot tell retrieval failures from generation failures
- A test set that is too small, too easy or entirely synthetic
- Trusting LLM-judge scores without human calibration
- Ignoring latency and cost while chasing quality

## Summary

- Measure retrieval (recall@k, MRR, nDCG) and generation (faithfulness, relevance, correctness) separately.
- Use a curated golden dataset plus calibrated LLM-as-judge, and run it in CI on every change.
- Feed production failures back into the dataset so the evaluation keeps improving.
